Building a comment overlay for prototypes

by Z. · September 14th, 2026 at 11:42 pm

new!

For months my design reviews went like this: spin up a prototype on some random port, screenshot it, paste it into chat, draw a wobbly red circle, and type “this, but less.” Context got lost at every hop. So I built claude-feedback, a tiny proxy that sits in front of any local dev server and paints a comment layer on top of it.

You open localhost:4599/5173/ instead of localhost:5173/, and the page looks exactly the same until you click. Every click drops a numbered pin, asks for a note, and saves a screenshot of exactly what you were looking at.

The whole trick is one route

proxy.js · javascript
  1. // every request to /5173/about is proxied to localhost:5173/about
  2. app.use('/:port/*', (req, res) => {
  3. const target = `http://localhost:${req.params.port}`;
  4. proxy.web(req, res, { target, selfHandleResponse: true });
  5. });
  7. // HTML responses get one extra line before </body>
  8. proxy.on('proxyRes', injectOverlay); // <script src="/__overlay.js">

Everything else is the overlay script: a fixed layer, a pin per comment, and a POST that appends to comments.json. Because the proxy owns the origin, the overlay works with any framework, from Vite to Next to a plain static server, without installing anything in the project itself.

Closing the loop

The part I didn't expect to love: the comments file is plain JSON, so my coding agent can read it. I say “address my feedback,” it pulls the unresolved comments for the current prototype, looks at each screenshot, fixes the thing, and flips resolved: true. Review becomes a to-do list with pictures.

Next up: threaded replies, and a keyboard-only mode so you can pin without a mouse.

What I learned shipping a daily news digest agent

by Z. · August 21st, 2026 at 7:05 am

Morning Briefing has run every weekday since spring. It reads a fixed list of outlets, picks the stories that matter to a specific group of readers, and writes a digest that lands before 7am. Here's what the first few hundred runs taught me.

  1. The protocol beats the prompt. Going outlet by outlet, in the same order, every day, was the single biggest quality jump. Free-roaming search found more stories and fewer good ones.
  2. Running stories need memory. A story that has been developing for two weeks deserves one line on what changed, not a fresh summary.
  1. Write the exclusions down. Most of the editorial judgment lives in what gets left out: duplicates, press releases, opinion pieces dressed up as news.
  2. Format is a feature. No bullets, no bold summaries, opinion clearly labeled. Readers noticed every single time I broke a rule.

A digest is an editorial product that happens to be automated, not an automation that happens to produce writing.

— from my notes, week 3

The agent is the easy part. The editor's rulebook is the product.

Notes on designing for motion

by Z. · June 9th, 2026 at 9:18 pm

I've been collecting rules of thumb for animation in interfaces. None of them are laws. All of them have saved a design of mine at least once.

  1. Motion should explain. If something moves, the movement should say where it came from or where it went.
  2. Fast in, faster out. Most UI transitions live between 150 and 300ms, and exits can be quicker than entrances.
  1. Ease like physics. Linear feels robotic. Ease-out feels like something arriving; ease-in feels like something leaving.
  1. Reduced motion is a design, not a switch-off. Swap slides for fades, keep the feedback, drop the parallax.

This very layout follows those notes: the tab loader, the lightbox and the ticker all calm down when your system asks for less motion.
