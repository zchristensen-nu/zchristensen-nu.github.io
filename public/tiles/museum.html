Essay Ipp. 12–27

Building a comment overlay for prototypes

On proxies, pins, and why a screenshot is worth more than the sentence written under it.

Z. ChristensenSeptember 20269 min read

I.The trouble with screenshots

When I review a prototype, the feedback travels a long way. I take a screenshot, draw a red circle on it, paste it into a chat, and then write a sentence explaining which red circle I meant. By the time anyone reads that sentence the page has usually changed, and the circle points at nothing.

I wanted the note to live on the page itself, attached to the element it was about, and readable by whoever (or whatever) fixes it next.

II.A proxy, not a plugin

The trick is to sit between the browser and the dev server. claude-feedback listens on port 4599; ask it for /5173/ and it forwards the request to localhost:5173, rewriting HTML on the way through to add a single script tag.Note 1HTML responses are buffered and decompressed before injection. Everything else, images and scripts included, streams straight through untouched. There is no framework integration and no browser extension. Any server, on any port, gets the overlay for free.

That constraint shaped everything after it. If the overlay can't assume React, or a build step, or even a particular page structure, it has to be small and polite: one script, no globals, styles scoped inside a shadow root.

III.Pins

Option-click anywhere and a pin drops. The script records what you typed, the viewport size, the scroll position, and enough about the element to find it again later.Note 2CSS selectors are kept only as a fallback. The primary anchor is the element's text plus its position among siblings, which survives most refactors. Pins stay put when you resize the window, and fade once they are marked resolved.

A comment is only useful if it still points at the thing you meant when someone finally reads it.

From the essay, p. 19

The first version anchored pins to pixel coordinates. It worked for exactly one afternoon, until I changed a font size and every note slid twelve pixels to the left of its subject.

IV.What the reader sees

Every comment saves a cropped screenshot next to the JSON.Note 3Screenshots are taken in the page with a canvas snapshot, so no headless browser is needed and the image matches exactly what the reviewer saw. When I ask my coding agent to address my feedback, it reads the file, opens each picture, fixes the issue, and sets resolved: true. The screenshot turns out to matter more than the words. "This feels cramped" is ambiguous; a picture of the cramped thing is not.

V.What I would change

Hot reload broke on day two, because websockets do not survive a naive proxy.Note 4The fix was to pass the Upgrade header straight to the target and pipe both sockets together, rather than trying to be clever about it. Threads are next, then a before-and-after view so a resolved comment can show what actually changed. For now it does one thing: it keeps the note next to the thing.

Notes

  1. HTML responses are buffered and decompressed before injection; everything else streams through untouched.
  2. Selectors are a fallback. The primary anchor is text plus sibling position.
  3. Screenshots use an in-page canvas snapshot; no headless browser.
  4. Upgrade requests are piped directly to the target server.
